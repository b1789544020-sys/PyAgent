# 架构与模型分工

## 数据流

```mermaid
flowchart LR
    A[TXT / Markdown / DOCX] --> B[受控导入与 DOCX 文字提取]
    B --> C[文档切块与 SHA-256 增量判断]
    C --> D[(SQLite)]
    C --> E[EmbeddingGemma 300M]
    E --> F[768 维本地向量]
    F --> D
    G[用户问题] --> H[BM25 / 中文词片 + 向量混合检索]
    D --> H
    H --> I{证据是否足够}
    I -- 否 --> J[明确拒答；不调用生成模型]
    I -- 是 --> K[Qwen2.5 3B 整理回答]
    K --> L{引用格式与编号是否有效}
    L -- 否 --> M[回退为原文检索]
    L -- 是 --> N[[S#] 引用与来源卡片]
    N --> O[只读全文定位与高亮]
```

## 各组件负责什么

### Qwen2.5 3B

通过本机 Ollama 调用，只接收当前问题及本轮检索证据。它负责把证据整理为简洁回答，并按要求附上 `[S#]`。它不直接维护 SQLite，也不负责生成 EmbeddingGemma 向量。

### EmbeddingGemma 300M

通过本机 Ollama 为文档块和查询生成向量。当前验证配置使用 768 维向量。向量模型不可用时，程序可以明确降级为关键词检索，不伪造向量分数。

### Python 与 SQLite

应用逻辑由 Python 实现，包括受控导入、DOCX OOXML 文字提取、切块、文件哈希、增量索引、BM25/中文二元词片、向量混合排序、证据阈值、引用校验、全文定位和移除备份。SQLite 保存来源、片段、定位信息及向量。

### 浏览器工作台

原生 HTML/CSS/JavaScript 通过回环地址上的本地 HTTP 服务访问真实后端。页面不直接读取任意磁盘文件，也没有把浏览器历史伪装成模型长期记忆。

## 框架选择

项目未使用 LangChain。上述检索、索引和引用链由项目自身的 Python 代码完成。这里的“导入资料并建立索引”是推理与检索准备，不是训练或微调 Qwen、EmbeddingGemma。
